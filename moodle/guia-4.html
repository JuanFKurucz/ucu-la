2. Qué es un framework: ladrillos o kit

  • Librería = ladrillos: armás todo vos (v0.2). Framework = kit: piezas que encajan, más rápido, pero a su manera.
  • La prueba: con una librería tu código la llama; un framework llama a tu código (tu @dynamic_prompt, sección 4). Es la inversión de control (Fowler).
Lo que hiciste a mano en v0.2 La pieza de LangChain
cargar_modelo() init_chat_model: ya lo usabas sin verlo, adentro de cargar_modelo (en llm.py)
Leer archivos Document loaders (PDF, web, Word…); la demo de LlamaIndex usa SimpleDirectoryReader
Buscar en Chroma Un retriever: dado un texto, trae fragmentos
Armar mensajes y llamar Un agente (create_agent), por ahora sin herramientas
Recordar la conversación (v0.2 no lo hacía: cada pregunta empezaba de cero) Un checkpointer: el cajón de las conversaciones
  • LCEL: pasos fijos encadenados con | (prompt | modelo | parser). Es tu con_rag como cadena (uv run python -m ejemplos.clase5 lcel; el 5 es el módulo M5). Para el agente, create_agent.

3. Memoria: cada conversación en su cajón

  • La API no recuerda nada: la app reenvía la conversación cada vez (LangChain — Short-term memory, lectura 2).
  • Cada conversación es un hilo con nombre (thread_id); el mueble de cajones es el checkpointer (persistencia). InMemorySaver se borra al cerrar el programa.
  • Riesgo: con el mismo thread_id, una persona ve la conversación de otra.
  • Hilo largo = más costo y tiempo. Recortar (trim_messages: olvida lo viejo) o resumir (SummarizationMiddleware: lo conserva a medias, una llamada más).
  • Para probar resumir en v03_memoria.py, dos cambios:
  • En la línea from langchain.agents.middleware import, sumá el nombre: … import ModelRequest, SummarizationMiddleware, dynamic_prompt.
  • En create_agent, cambiá middleware=[con_contexto] por middleware=[SummarizationMiddleware(cargar_modelo(), trigger=("messages", 6), keep=("messages", 2)), con_contexto].

  • Medido (modelo falso, un hilo): llega a 6 mensajes y en la siguiente baja a 4 (resumen, los 2 últimos y la nueva). Sin gastar: uv run pytest tests/test_resumen.py (2 passed; en tu repo, 1 passed, 1 skipped: el otro lee esta guía).

  • La prueba de memoria es contar mensajes por hilo, no la respuesta: el RAG puede contestar bien sin recordar nada.

  • Medido (uv run python v03_memoria.py, dos veces, Gemini 3.5 Flash-Lite): el seguimiento de A dio NO ENCONTRADO una vez y bien la otra; B, sin historia, bien las dos. La cuenta (A: 4, B: 2) no cambió.
  • La búsqueda usa solo el último mensaje: «¿Y qué pasa con eso…?» busca sin saber qué es «eso». La memoria ayuda a responder, no a buscar.
  • Arreglo habitual (v0.3 no lo hace): reescribir el seguimiento como pregunta completa antes de buscar; una llamada más.
  • Al revés: puede citar un documento que no está en fuentes porque lo vio en la respuesta anterior.

4. Python de hoy: el @ arriba de una función

@dynamic_prompt
def con_contexto(pedido):
    docs = buscador.invoke(pedido.messages[-1].text)  # busca con el último mensaje
    contexto = "\n\n".join(f"[{d.metadata['doc']}]\n{d.page_content}" for d in docs)
    return f"{SISTEMA}\n\nContexto:\n{contexto}"  # esto lee el modelo
  • Es la de v03_memoria.py (sin la línea que anota las fuentes). En el archivo, def con_contexto(pedido: ModelRequest) -> str: lleva pistas de tipo (Python no las exige).
  • La línea con @ es un decorador: una etiqueta que le dice al framework cuándo usarla. Esta: «corré esto antes de cada llamada al modelo y usá lo que devuelva como instrucciones». Es tu RAG de v0.2, dentro del kit.
  • Lo que corre antes o después de cada llamada es middleware (LangChain — middleware).

En la clase que viene aparece @tool, que convierte una función en herramienta.

No entiende el seguimiento Las dos preguntas tienen que usar el mismo hilo. Y la búsqueda solo ve el último mensaje (sección 3): mirá qué fuentes trae.

Un error del proveedor: «429…», «503…», «500 o 504», «Sin conexión…», «404…» o «sin saldo» Son los mismos de la clase 2 y se arreglan igual: «Si te trabás» de la guía 2, una fila por error.
